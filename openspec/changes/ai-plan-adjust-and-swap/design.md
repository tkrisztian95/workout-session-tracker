## Context

The app is a client-only Next.js/React PWA. Plans are edited through `PlanForm`, which is reused for both creating a new plan and reviewing/editing an existing one (including a plan just generated by `AiPlanSuggestionModal`). An LLM layer already exists under `src/lib/ai/`: a shared `callOpenAI` client, versioned prompts, and `suggestPlan` / `importSessions`. This change extends that layer to refine an _existing_ plan rather than create one.

## Goals / Non-Goals

**Goals:**

- Whole-plan adjustment from a preset or free-text instruction, with a preview before applying.
- Single-exercise swap from any plan exercise row, with a preview before applying.
- Reuse the existing `callOpenAI` client, prompt-versioning convention, and muscle normalisation.
- Work entirely client-side with the user's own key; no new dependencies.

**Non-Goals:**

- Backend or server-side proxying.
- Persisting AI changes automatically — the user still saves the plan via the existing Save action.
- Conversational multi-turn editing or undo history.

## Decisions

### Two operations, one prompt module

`adjustPlan` returns a full reworked plan (same JSON shape as `suggestPlan`); `swapExercise` returns a single exercise. Both live in `src/lib/ai/adjust.ts` with system prompts in `src/lib/ai/prompts/adjust/v1.ts`, following the existing `prompts/<feature>/vN.ts` + `index.ts` convention.

### Plan context is the human-readable summary, not raw JSON

Both operations send `summarisePlan()` (already used by `suggestPlan`) as context. IDs are intentionally **not** round-tripped: `PlanForm` replaces its `days` / `sharedExercises` state wholesale on adjust, and swap matches by the original exercise's `id` locally. The LLM never needs to echo IDs, which keeps the prompt smaller and the response more reliable.

### Swap preserves role and identity locally

`swapExercise` does not ask the model for `role`; the replacement inherits the original exercise's `role`. `PlanForm.handleAiSwap` replaces the exercise in place, keeping the **original `id`** so React state and ordering are stable.

### Validation reuses `AiValidationError`

Both prompts emit `valid` / `validationError`, parsed into the existing `AiValidationError` so non-fitness instructions surface the same "rejected" UI as the suggestion and import flows.

### Entry points gated on configured AI

`PlanForm` reads `getLlmConfig()` once; the "Adjust with AI" button and per-row swap icons render only when an API key exists, matching how the rest of the app treats AI as opt-in.

## Risks / Trade-offs

- **LLM may rewrite more than asked.** Mitigated by prompt guidance ("apply ONLY the requested adjustment") and by always showing a preview the user must confirm.
- **Lost IDs across an adjustment** mean per-exercise React state (e.g. expanded schedule) resets. Acceptable: an adjusted plan is conceptually a new draft and the user reviews it anyway.

## Migration

None. Additive UI and a new AI module; no storage or type changes.
